# NATS 通信设计参考笔记

- 日期：2026-10-17
- 状态：**仅作设计参考；当前方案为自定义 WS 转发网关。**
- 关联：[需求梳理](./requirements.md)、[技术设计与实施计划](./technical-design-and-implementation-plan.md)。
- 范围纠正：用户要求参考 NATS 的通信设计，没有提出采用 NATS、替换网关或开展 NATS 对照原型。此前把它扩展为选型讨论，并把其特有行为列为当前风险，不符合本次审查范围。

## 1. 参考的目的

参考成熟通信系统时，只提取有助于检查当前设计的问题：谁负责寻址、谁关联请求和结果、谁判断失联、如何限制慢连接、恢复连接是否改变旧调用。是否存在风险，必须回到当前需求和设计找到对应规则及具体触发时序。

本项目的评估对象是：两端主动连接、自定义 WS 网关、静态一对一绑定、在线透明转发、不缓存业务消息、不补发、不重试旧调用，以及端点负责的超时和尽力取消。

## 2. 当前设计对这些问题的回答

| 审查问题 | 当前方案已有安排 | 设计位置 |
| --- | --- | --- |
| 谁决定请求发给谁？ | 凭证映射到静态绑定，再找到对端当前有效连接；同身份拒绝第二条有效连接。 | 技术设计第 4 节 |
| 谁关联调用和结果？ | 两端使用通道 epoch 与调用 id；网关不维护业务调用表。 | 第 3、4、6 节 |
| 发不出去怎么办？ | 当次失败，不保存到下一条连接；恢复只服务新调用。 | 第 4、5 节 |
| 谁识别失联？ | 各端保活与网关通道状态通知；端点结束等待并尝试取消。 | 第 5、6 节 |
| 慢连接会不会拖住其他绑定？ | 每连接有界写入、独立处理，禁止持全局注册表锁做网络 I/O。 | 第 4、5 节 |
| 会不会无限重连？ | 最小版使用本次运行的固定重拨额度及有限拨号／等待时间，成功不重置额度。 | 第 5 节 |

这些是已有设计安排，不能重复列为“设计没有考虑”的问题。当前[一对闭环](./step-1-results.md)、[两组并发隔离](./step-2-pair-isolation-results.md)、[明确断线与有限重连](./disconnect-reconnect-results.md)及[心跳与静默失联](./heartbeat-silent-loss-results.md)已验证；其余能力仍按后续步骤实施。

## 3. 不适用的风险推导

当前方案不使用 NATS 客户端、subject、订阅或 queue group。此前围绕 SDK 重连缓存、订阅扇出和按服务器计数等机制提出的 P1—P6，不再作为当前项目的风险清单；NATS 专用 N1—N10 对照实验与选型待办也不属于当前计划。

当前方案的具体设计复核已记录在[技术设计第 9 节](./technical-design-and-implementation-plan.md#9-设计复核结论)，区分待补规则、已有防护和已接受的取舍。后续审查以该方案及用户决策为依据。
