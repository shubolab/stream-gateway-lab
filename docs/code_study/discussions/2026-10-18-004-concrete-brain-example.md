## 源码可见事实

1. `main.go` 的 `run` 从命令行读取 `-message`、`-wait-ms`，把文字和时长交给 `runBrain`。本例的 800 是操作者指定的 800 毫秒，即 0.8 秒。
2. A-only 是 echo 输入中的普通文字。选择配对使用另一个 `-pair` 参数，网关不解析 message 的英文含义。
3. `runBrain` 写死先 echo 后 wait，不调用真实模型。`executeTool` 的 echo 分支复制整份输入，因此 `wait_ms` 也原样返回。
4. `runBrain` 从 echo 的返回中取 `wait_ms`，改用 wait 工具要求的字段名 `ms`；没有依据文字推理等待时长。
5. 远程模式下，`RemoteExecutor.Call` 在 Brain 进程里发送调用并等结果；Executor 进程内的 `executeTool` 才实际执行工具。
6. 网关的 `pairRoute.ServeHTTP` 校验外层信息并转发原始消息；echo 之后发起 wait 的仍是大脑。
7. `client.send` 只报告发送是否出错。执行端 `receive` 启动 goroutine 后返回；工具输出由那个 goroutine 另外发成 result 消息。Brain 收到、匹配结果后，等待中的 Call 才返回输出。
8. `waited_ms` 填的是请求时长，不是实际端到端耗时的测量值。

逐步源码定位、完整数据、消息格式和图见[从输入走完 echo → wait](../07-concrete-call-walkthrough.md)。

## 本轮解释观点及修正

**助手修正：**此前“根据返回中的 800 决定下一步等待多久”的表述过于概括。具体实现只是“读取前一次工具返回的字段，再填入下一次工具参数”，不应让人以为模型推导出了 800。

**助手对模拟作用的解释：**echo → wait 的实用业务价值很有限，但它提供了一条容易核对的“前次工具结果 → 下次工具参数”路径。结合已有需求，可用来观察同一段流程在本地和远程执行方式下是否保持相同的调用体验。它不能证明真实模型会规划任务。

**本轮采用的讲解顺序：**操作者填了什么 → 两个工具分别做什么 → 大脑怎样串起两步 → 远程时每一端收到什么 → 再补函数名和协议外层。暂时先走成功路径，避免在最初例子中混入重连、取消和各种 ctx。

这些属于解释方式与阅读观点的调整，没有形成更换模拟流程或重构接口的设计决定。
