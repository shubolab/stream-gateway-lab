## 当前源码可见事实

依据 [`gateway.go`](../../../internal/gateway/gateway.go) 中的 `PairRoute`、`ServeHTTP`、`Remove` 和 `closePeerConnectionsLocked`：

- 每组 pair 使用独立的 `Mu`，共同保护 `Peers`、`Peer.Conn` 和 `Epoch`。连接接入、消息转发和断线清理都要协调这份共享状态。
- `pair`、`tokens` 以及网关的 `Pairs` 路由表在初始化后只读；读取 WebSocket 消息时不持有 `PairRoute.Mu`。
- 当前状态通知、消息转发和部分清理操作会在持锁期间写入网络，也有日志输出。单次写入有 2 秒超时，但这不代表整个持锁区间最多持续 2 秒。

## 后续评估范围

1. 覆盖多组 pair 并发、单组高频连续调用、慢接收端，以及转发期间断线和重连的场景；保持现有每组一次一个工具调用的限制。
2. 记录吞吐、端到端延迟（包括 P95/P99）、锁等待及持有时间、网络写入耗时，以及断线清理和重连耗时；结合 mutex/block profile 定位等待来源。
3. 优先判断持锁执行网络写入、日志输出等操作是否形成瓶颈，再评估缩短持锁范围。不能仅凭多个职责共用一把锁，就认定需要拆锁或更换锁类型。
4. 如需改造，仍须保证连接关系与 epoch 一致、就绪通知先于对应业务消息、旧连接清理不影响新会话，以及旧调用不重放；通过既有正确性回归和相同负载下的前后对比验证。

## 结论边界

本次只登记后续工作。尚无专项压测数据，不能宣称这把锁已经构成性能瓶颈，也未采纳拆锁、发送队列或其他具体改造方案。
